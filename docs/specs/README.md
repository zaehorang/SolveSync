# 동작 명세

> **Description**: 각 Coding Platform 연동을 그 기술을 모르는 사람이 검수할 수 있도록 관측 가능한 동작으로만 기술한 명세 모음이다. 구현 계약은 [`docs/platforms/`](../platforms/README.md)를 따른다.

이 폴더의 문서는 [`docs/platforms/`](../platforms/README.md)를 **대체하지 않는다.** 두 문서는 독자가 다르다.

| | `docs/specs/` (이 폴더) | `docs/platforms/` |
|---|---|---|
| 독자 | 그 기술을 모르는 사람 | Adapter를 고칠 사람 |
| 답하는 질문 | 사용자에게 무엇이 보이는가, 이게 맞는 동작인가 | 어느 DOM 사실 위에 무엇을 구현했는가 |
| 담는 것 | 발동 계기, 입력, 결과, 경계 상황, 손으로 확인 가능한 검증 항목 | selector, 관찰 날짜, mutation 순서, 식별자 형식 |
| 담지 않는 것 | 클래스·메서드 이름, 코드 블록, 프레임워크 용어 | 사용자 관점 재서술 |

둘이 어긋나면 **구현이 무엇을 하는지는 `docs/platforms/`가 맞고, 그것이 옳은 동작인지는 이 폴더의 열린 질문으로 올린다.**

## 무엇이 어디에 있나

명세는 **사용자가 겪는 순서대로 다섯 자리**로 나뉜다. 같은 자리의 파일은 세 사이트에서 이름이 같으므로, 한 자리를 골라 가로로 읽으면 세 연동의 차이가 그대로 드러난다.

| 자리 | 하는 일 | LeetCode | Programmers | SW Expert Academy |
|---|---|---|---|---|
| 1 | 정답을 언제 새로운 것으로 세나 | [정답 감지](leetcode/accepted-detection.md) | [정답 감지](programmers/accepted-detection.md) | [정답 감지](swea/accepted-detection.md) |
| 1.5 | 어느 문제인지 가려내기 | 주소로 정해져 별도 명세 없음 | 주소로 정해져 별도 명세 없음 | [문제 식별](swea/problem-identity.md) |
| 2 | 올릴 풀이를 어디서 얻나 | [풀이 확보](leetcode/solution-source.md) | [풀이 확보](programmers/solution-source.md) | [풀이 확보](swea/solution-source.md) |
| 3 | 얻지 못하면 무엇이 보이나 | [확보 실패](leetcode/source-failure.md) | [확보 실패](programmers/source-failure.md) | [확보 실패](swea/source-failure.md) |
| 4 | 이미 올린 것과 같으면 | [같은 풀이 중복 방지](common/duplicate-prevention.md) — 셋 공통, 판정 기준만 갈린다 | | |
| 5 | 저장소 어디에 어떤 모양으로 | [저장 위치와 목록](common/repository-layout.md) — 셋 공통, 파일명·난이도 칸만 갈린다 | | |
| — | 저장에 실패한 뒤 다시 올리기 | [다시 시도](leetcode/retry.md) | 해당 없음 | 해당 없음 |

**4번과 5번이 공통 파일인 이유**는 세 사이트가 실제로 같은 동작을 하기 때문이다. 사이트별로 쪼개 두었을 때 이미 어긋나 있었다 — 목록 정렬 순서와 목록 문서를 처음 만드는 동작이 한 사이트 문서에서만 빠져 있었다. 공통 로직을 세 번 적으면 반드시 한 번 어긋난다. 갈리는 부분은 각 공통 명세 안의 **차이 표**에 모았다.

**1번과 2번이 사이트마다 따로인 이유**는 그 자리에서 세 연동이 진짜로 다르기 때문이다. 감지는 상태를 드는지가 갈리고, 풀이 확보는 서버 조회(LeetCode) · 그 자리에서 읽기(Programmers) · 기다렸다 받기(SW Expert Academy)로 성격 자체가 다르다.

**LeetCode에만 3번 뒤에 다시 시도가 있고**, **SW Expert Academy에만 1.5번이 있다.** 전자는 조회에 성공한 뒤의 저장 실패에서 다시 올릴 수 있기 때문이고, 후자는 모든 문제가 같은 주소를 써서 문제를 가려내는 일이 독립 동작이 되기 때문이다.

## 검수하는 법

각 명세의 `Acceptance` 항목은 **화면만 보고 손으로 따라 할 수 있게** 쓴다. 코드를 열어야 확인할 수 있으면 그것은 검증 항목이 아니라 결과 서술이다.

`열린 질문`은 코드만으로 답이 나오지 않아 사람에게 물어야 하는 것이다. 답이 정해지면 그 질문을 지우고, 결정이 동작을 바꾸면 해당 source of truth를 먼저 고친 뒤 명세를 갱신한다.

같은 자리의 명세를 세 사이트에서 나란히 읽으면 연동 사이의 차이가 드러난다. 공통 명세에서는 그 비교가 이미 차이 표로 들어 있다 — 특히 중복 방지는 결론이 갈린다. LeetCode는 제출마다 번호가 달라 같은 코드를 다시 내면 커밋이 하나 더 생기고, 나머지 둘은 코드 내용이 판정에 들어가 커밋이 생기지 않는다.

## 새 명세를 쓸 때

파일 단위가 아니라 "사용자 눈에 하나로 보이는 동작" 단위로 자른다. 경계가 애매하면 "이 동작만 사라지면 사용자가 무엇을 못 하게 되는가"로 물어 답이 한 문장이면 하나의 기능이다.

플랫폼 폴더 아래에 두고 파일 이름에는 플랫폼 이름을 넣지 않는다. 폴더가 이미 말하는 것을 파일 이름이 반복하면 목록이 접두사로 뒤덮인다.

**같은 자리의 파일은 세 사이트에서 이름을 같게 쓴다.** 성격이 달라도 그렇다. 이름이 갈리면 가로로 읽을 수 없고, 그 자리가 같은 자리라는 사실이 보이지 않는다. 성격 차이는 파일 안의 Description 한 줄로 말한다.

세 사이트가 실제로 같은 동작을 하면 `common/`에 하나로 두고 갈리는 부분만 차이 표로 적는다. 사이트마다 따로 적는 것은 그 자리에서 동작이 진짜 다를 때뿐이다.

작성 규칙과 자동 검사는 `behavior-spec-extraction` 스킬이 들고 있다. 구현 용어가 새어 들어갔는지, 검증할 수 없는 항목이 있는지를 그 스킬의 린터가 잡는다.
